# Media storage and image lifecycle

This document describes how generated images are stored, validated, prepared, and served.

The V1 upload-image publishing workflow is unchanged. Instagram still fetches a public HTTPS JPEG through `upload_image` / `GET /api/v1/media/{filename}`. Generated images use a separate owner-scoped lifecycle.

## Directories

All generated-image files live under `media_root` (default `storage/`):

```text
storage/
    generated/{user_id}/img_<uuid>.png
    prepared/{user_id}/img_<uuid>.jpg
    published/{user_id}/img_<uuid>.jpg
```

- `generated/` holds the original provider output (JPEG or PNG).
- `prepared/` holds the Instagram-normalized JPEG produced by the existing V1 `ImagePreparer`.
- `published/` holds a copy of the prepared JPEG after a verified publish.

User ids and filenames are generated or validated internally. User-supplied filesystem paths are never used.

Internal names look like:

```text
img_3f1a9c0e2b8d4a119c6e7f0ab1d2c345.png
```

## Path safety

`services/media_paths.py` is the only module allowed to resolve generated-image locations.

Rules:

- User ids are sanitized to `[A-Za-z0-9_-]` (so `../etc/passwd` cannot leave `media_root`).
- Filenames must match `img_<32 hex>.(png|jpg|jpeg)`.
- Resolve the path and require it to stay inside `media_root`.
- Write atomically (`*.tmp` then replace). Partial files are deleted on failure.

V1 public hosting (`tools/image_storage.py`) still stores Instagram-fetchable JPEGs under `storage_dir` and continues to reject path traversal in `resolve_public_file`.

## Validation

`tools/image_validator.py` is reused for both uploaded and generated images.

Supported formats: JPEG and PNG.

A file is accepted only when all of the following succeed:

| Check | Source of truth |
| --- | --- |
| MIME type | Claimed MIME, if present, must be JPEG/PNG |
| File signature | JPEG `\xff\xd8\xff` or PNG `\x89PNG\r\n\x1a\n` |
| Readability | Pillow `verify()` then `load()` |
| File size | Configured `max_image_bytes` (default 8 MB) |
| Dimensions | Positive, within min/max sides |
| Corruption | Decode errors become `CORRUPTED_IMAGE` |

The extension is ignored. A JPEG named `.gif` is still a JPEG. A JPEG whose claimed MIME is `image/png` or `image/gif` is rejected.

## Preparation

Generated images are normalized with the existing V1 `ImagePreparer`:

- Original generated bytes are not overwritten.
- Output is a deterministic JPEG.
- Instagram photo constraints are unchanged: aspect ratio between 4:5 and 1.91:1, target width 1080, quality/size cap 8 MB.
- `prepare_to()` writes into `storage/prepared/{user_id}/` without changing the V1 `prepare(path, task_id)` destination (`output/prepared/{task_id}.jpg`).

## Lifecycle

```text
GENERATED
  → VALIDATED
    → PREPARED
      → READY_FOR_APPROVAL
        → APPROVED
          → PUBLISHING
            → PUBLISHED
```

Failure states (terminal):

- `GENERATION_FAILED`
- `VALIDATION_FAILED`
- `PREPARATION_FAILED`
- `PUBLISH_FAILED`
- `AMBIGUOUS_PUBLICATION`

`MediaStorageService.ingest_generated()` stores the original, validates it, prepares it, and leaves it `READY_FOR_APPROVAL`. Approval and publish transitions are explicit so later agents can call them without bypassing the Instagram Agent.

Only a verified successful publication should be copied into `published/` and marked `PUBLISHED`.

## API

Owner-scoped routes:

- `GET /api/v1/generation` — list the current user's generated images
- `GET /api/v1/generation/{image_id}` — fetch one record
- `GET /api/v1/generation/{image_id}/media` — serve generated/prepared/published bytes

Responses never include filesystem paths. The public payload has `media_url` such as `/api/v1/generation/{id}/media`.

Authentication is required. User A cannot list, read, or fetch User B's files. Missing or foreign ids return 404.

V1 routes are unchanged:

- `POST /api/v1/instagram/publish`
- `GET /api/v1/media/{filename}` (public JPEG for Instagram)

## Integration

The OpenAI image provider was not modified. It already depends on `GeneratedImageStore.save()`. `MediaStorageService.save()` implements that contract, and `create_app()` injects the shared media service as the provider's storage backend.

`LocalGeneratedImageStore` delegates to `MediaStorageService` so generated files always enter the lifecycle.

## Cleanup

`MediaStorageService.cleanup(user_id, image_id)` deletes generated, prepared, and published files for that record plus the metadata entry. Failed writes delete `*.tmp` leftovers.
